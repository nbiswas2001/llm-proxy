# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```sh
cargo run -- --config config.toml       # run (config.toml is gitignored; copy config.example.toml)
cargo run -- --check                    # validate config and exit without binding a port
cargo test                              # all tests
cargo test routes_alias_and_rewrites    # a single test by name substring
cargo clippy --all-targets              # kept at zero warnings
cargo fmt
```

`-v` logs a line per request (route, status, timing); `-vv` adds bodies and per-chunk
tracing. `log_filter` in `main.rs` maps the count to a filter string, and `LLM_PROXY_LOG`
overrides it entirely. Per-request logging lives at DEBUG so the default run stays quiet -
new request-level logging belongs there too, not at INFO.
`--port` / `--host` override the config file. Secrets live in a gitignored `.env`
(`.env.example` is the template); `--env-file` points at a different one. `--balance`
queries the active provider's credit and exits, like `--check` binding nothing; it owns
stdout, so its filter defaults to `off` and logging is written to stderr - keep the report
itself on `println!` and everything else on `tracing`.

Rust edition 2024; the code uses let-chains, so it needs a recent stable toolchain.

## Architecture

One job: accept requests on `:8600`, forward them to a configured upstream provider with the
real API key attached, and stream the response back. The protocol on the way in is whatever
the active provider speaks - OpenAI's, or Anthropic's when it is marked `api = "anthropic"`;
nothing is translated between them. Three files do that; `balance.rs` is a side errand that
never runs while serving.

**`src/proxy.rs` — the forwarder.** `proxy()` is registered as the router's `fallback`, not
as a set of endpoint routes. That is deliberate: the proxy never needs to know which OpenAI
endpoint is being called. Any path is forwarded verbatim, so `/v1/embeddings`, `/v1/models`,
`/v1/responses`, and endpoints that do not exist yet all work without code changes.
`/health` is the only explicit route.

The request lifecycle:

1. Client auth (`client_auth_error`) — only enforced when `server.api_keys` is non-empty.
2. Body is read whole and parsed as JSON *only* to read `"model"` and `"stream"`; nothing
   is written back. A non-JSON body is forwarded untouched.
3. The body is forwarded unchanged to `Config::active()`; the parse above only feeds the
   log line and the streaming-header decision.
4. Headers are copied minus `STRIPPED_REQUEST_HEADERS` + `HOP_BY_HOP`; the client's
   `Authorization` and `x-api-key` are dropped and replaced with the provider's key -
   as a bearer token, or as `x-api-key` when the provider is `api = "anthropic"`.
   `accept-encoding` is stripped so upstream never compresses a stream we relay.
5. The response is re-framed as `Body::from_stream(...)` — this is what makes streaming
   incremental rather than buffered. Because the body is re-framed, `content-length` must be
   dropped from the response headers (`is_stripped_response_header`).

An Anthropic provider is the one place a header is *invented*: `needs_anthropic_version`
adds `anthropic-version: 2023-06-01` only when neither the client nor
`[providers.<name>.headers]` supplied one, since a second copy of that header is an upstream
400 and a client pinning a version must keep its own. That is the entire extent of protocol awareness in `proxy.rs` -
the body is still forwarded byte for byte, so an Anthropic-shaped request only works
because the client sent one.

The body is wrapped in `LoggedStream`, which counts bytes and chunks as they pass and logs
once the stream ends. Its `Drop` impl covers the client-hangup case, which `poll_next` never
sees — that is the only way an aborted stream gets reported.

Errors are returned in OpenAI's `{"error": {...}}` shape via `error_response`. Upstream
status codes and error bodies pass through unchanged; only transport failures become
502/504 generated by the proxy.

**`src/config.rs` — provider selection.** Exactly one provider carries `active = true` and
serves every request; `validate_and_expand` enforces that and stores the winner in
`active_name`, so `Config::active()` is infallible afterwards. Only the active provider is
env-expanded and key-checked — an inactive one may reference a variable that does not exist,
which is what makes keeping several providers in the file cheap. There is deliberately no
model routing, alias table, or model list: the request body, model name included, is
forwarded byte for byte. `reject_stale_prefix` exists only to catch a leftover
`"<provider>:<model>"` name from an inactive provider and answer with a clear 400 instead of
passing a nonsense model upstream.

`Provider::api` (`Api::Openai` / `Api::Anthropic`) is the only protocol knowledge in the
config: it picks the auth header in `proxy::apply_provider_auth` and gates the version
default. It is *required* on every provider, with no serde default - inferring it from the
host would be wrong for Anthropic's own OpenAI-compatible endpoint, and a wrong guess shows
up as a 401 from upstream rather than a startup error. Because the whole file is
deserialized (only *validation* is scoped to the active provider), an inactive provider
needs the field too. `parse` appends a hint to the bare "missing field `api`" that serde
produces; it is the only error message the config module dresses up, which is what a
mandatory field with two legal values earns.

`Provider::upstream_url` joins `base_url` with the request path while collapsing a duplicated
version segment (base `.../v1` + path `/v1/chat/completions` must not yield `/v1/v1/...`).

All config structs use `#[serde(deny_unknown_fields)]`, so a typo'd key is a startup error
rather than a silently ignored setting — adding a config option means adding the field.
`expand_env` handles `"${VAR}"` / `"env:VAR"` only as a *whole* string, not interpolated
within one. It resolves against the process environment, which `load_env_file` has already
populated from `.env` (real environment variables win — `dotenvy` does not override). A key
that resolves to empty is a startup error, since an unfilled `.env` line would otherwise
send `Bearer ` upstream and fail as a confusing 401.

**`src/balance.rs` — `--balance`.** The one place that is *not* protocol-agnostic: there is
no balance endpoint in the OpenAI protocol, so this is per-provider knowledge. `known_for`
matches on the **host** of `base_url` (not the whole URL) and yields a built-in endpoint plus
a parser for its documented response — DeepSeek's `/user/balance`, OpenRouter's
`/api/v1/credits` (with `/api/v1/key` as a best-effort second call for a key-scoped cap; its
failure is logged at DEBUG and never sinks the report). Endpoints are built from the
*origin* of `base_url`, since they sit beside `/v1` rather than under it — that is why
`upstream_url` is not reused here. A `[providers.<name>.balance] url` in the config wins over
the table and prints the raw JSON pretty-printed, which is the escape hatch for a provider
the table does not know. The response structs are deliberately lenient (no
`deny_unknown_fields`, unlike the config structs), so a new field upstream is not a parse
error. Anything that fails — unknown provider, refused key, unexpected body — is an `Err`,
so the flag is scriptable. Requests go out through `proxy::apply_provider_auth`, the same
helper the forwarding path uses, so a provider's extra headers apply here too.

**`src/main.rs`** loads `.env` *before* initializing logging — so `LLM_PROXY_LOG` can be set
there too — then wires the CLI, builds the shared `reqwest::Client` (its `timeout` covers a
whole streamed response, hence the 600s default), and constructs `AppState { config, http }`.

## Testing

Unit tests live in `#[cfg(test)] mod tests` at the bottom of `src/config.rs`,
`src/proxy.rs`, and `src/balance.rs`, and cover routing precedence, URL joining, client
auth, the per-protocol auth headers, and balance endpoint/response handling. The proxy
tests build a `reqwest` request and inspect its headers, so they need no server. The balance
tests parse captured sample payloads and never touch the network — a new provider added to
`known_for` should come with its documented payload as a test. There is no integration-test
harness; to verify forwarding and streaming end to end, run a throwaway HTTP server that
emits chunked SSE with a delay between chunks, point a config's `base_url` at it, and check
that the client observes that same delay between chunks (buffering anywhere would collapse
them).
The same trick, with a server that echoes back the headers it received, is how the Anthropic
header shaping was checked against a running proxy.
